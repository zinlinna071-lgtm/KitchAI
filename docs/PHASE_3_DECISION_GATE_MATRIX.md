## Cross-cutting implementation gates (not owner-choice substitutes)

These technical gates apply regardless of which D3 options are selected:

1. **Canonical stock truth:** document whether an append-only movement ledger is authoritative; derived balances must be reconcilable and rebuildable or an alternative must be explicitly justified.
2. **Atomic posting:** one local IndexedDB transaction must persist the production aggregate and durable outbox; separately, the remote aggregate command must commit atomically and idempotently. Independent ordered upserts are not an atomic production operation.
3. **Movement semantics:** define quantity sign/direction, zero rejection, correction/reversal linkage, event identity, and precision before writing stock.
4. **Lot allocation:** any disposition that consumes finished stock must identify lots explicitly until an allocation policy is reviewed; allocations must sum exactly to the disposition quantity.
5. **Migration safety:** test an upgrade from a populated current `kitchai-business-data` v2 database, preserving entities, outbox/operations, sync metadata, conflicts, migration ledger, and legacy source records.
6. **Scope and time:** validate owner/business scope locally and remotely; define timestamp, timezone, and business-day semantics.
7. **Repository grounding:** map every proposed store/index/API/migration change to existing code and tests before creating an implementation prompt.
8. **Evidence honesty:** local/emulated tests do not prove hosted authorization, real cross-device sync, backup/restore, or production readiness. No hosted provisioning, billing, secrets, or deployment is authorized by these planning documents.
